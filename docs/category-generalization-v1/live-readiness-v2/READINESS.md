## Reference-free arithmetic — investigation and smallest safe plan

Historical cause: `scripts/multitask_policy42.py` supplied the exact independently computed sum as `reference` for every arithmetic sample, then captured/fitted the four-candidate planning context with that reference. `VerifierSelector.plan` derives reference availability and Semantic eligibility from context. `PlanningContext.compatibility_id` includes reference availability, candidate prerequisite/exclusion state and eligible roster, alongside requirements, reputation, costs, resources, budget and execution obligations. Zero probability on Semantic does not erase these contract fields.

Rule capability: `app/verifiers/rule_verifier.py:verify` accepts optional context but does not use it in its arithmetic checks. Its anchored parser extracts two signed numeric operands and an implemented operator; Decimal independently computes the expected value. Addition/subtraction/multiplication use exact Decimal comparison (precision 50); division uses the existing answer-decimal-place half-up rounding contract. This is bounded parser support, not general mathematical reasoning. A narrow initial addition contract avoids implicitly certifying every implemented operation or wording.

Representation: the current question analyzer classifies `What is 4 + 4?` as atomic arithmetic with context absent. Selector metadata represents `reference_available=False`; Rule remains eligible and reference-independent, while Semantic becomes ineligible with `missing_reference`. The new metadata-only regression proves that requirements stay the same while compatibility ID changes. No analyzer, selector or teammate-owned verifier edit is needed to express this task. Existing ReusablePolicyGameRuntime rejects absent reference against the historical reference-present artifact, as required; a separately bound reference-absent artifact can express the other contract without removing the check.

A **new independently fitted artifact is required under the current certified-contract machinery**. The old matrix was collected with reference-present candidate inputs; deleting a context flag or copying probabilities does not supply independent evidence for a different contract. A formally reviewed transfer proof could be a future alternative, but none currently authorizes reference-free execution, and this task neither introduces nor assumes one. No fitting is performed now.

Smallest future implementation, subject to separate research/execution approval:

1. Declare an opt-in versioned `reference_free_addition_v1` scope, initially two bounded signed integer operands (e.g. absolute value <=10000), existing accepted question grammar and numeric-only answer. Context must be absent; no internally synthesized reference is attached to the runtime request. Ground-truth labels belong only to offline dataset custody. Expand decimals/other operations only after separate contract tests and certification. Preserve all old exact-route defaults and frozen resource identities.
2. Create a new offline planning/resource/execution package for explicitly registered Rule-only candidates, arithmetic requirement, reference absence and explicitly reviewed minimum-selected/minimum-informative counts of one. Use existing contributor/coverage checks with that new contract; never weaken historical contracts or borrow their singleton transfer ID. Pin actual Rule implementation/configuration and a new evidence provenance chain. No model, corpus, index or Ollama dependency is needed for this new roster. If more candidates are desired, that is a larger independently resourced experiment, not the smallest path.
3. Fit once per supported task/context class using owned offline tools and independently collected reference-absent reports. A Rule-only feasible strategy produces a degenerate distribution; do not claim a demonstrated team-game benefit from it. Retain the existing aggregation semantics. Register its new policy/artifact/compatibility/version IDs under the new scope; never refit per question or relabel the old fitted distribution.
4. Prepare disjoint operand-pair groups for history/cost characterization, development/payoff fitting and untouched held-out evaluation. Group commutative pairs and their wording variants together to prevent leakage. An initial bounded proposal is 32 history, 32 development and 64 held-out question groups, each with independently labeled correct and incorrect candidates: 256 Rule attempts total, zero model generations, before any extra guard/malformed fixtures. Dataset size is a proposed pilot, not proof of sufficient statistical power; acceptance sample size must be chosen against a predeclared false-accept bound/confidence interval. Freeze history, development choices, attack design, costs, budgets, thresholds and policy before unlocking held-out results. Independent integer/Fraction labels must not call Rule or copy its reports.
5. Include zero, negative operands, cancellation, equal operands, numeric formatting, bound edges, paraphrase and entirely unseen operand pairs. Add separately labeled malformed answers, off-by-one/sign errors, unsupported/multiple-expression prompts, context supplied unexpectedly, resource/source mismatch, budget exhaustion, no contributors, provenance failure and interruption/journal cases. Unsupported inputs should be routed unavailable, not counted as factual rejects. Decimal/division rounding expectations need explicit contract review before expanding scope.
6. Predeclare correct accept/reject counts, false accepts/rejects with uncertainty intervals, abstention/uncertainty, decision and capability coverage, weighted decision loss, attempt counts and measured CPU/wall costs, including startup separately. Require no known false accepts in the bounded suite, but do not equate zero observed errors with zero population error. Choose numeric acceptance thresholds/sample sizes before collection. Run mock service/API-boundary checks plus bounded approved real Rule runs, then repeat all 69 historical route projections. Activation remains a separate backend/runtime-owner task.

Exact-first routing remains mandatory. Thus an existing registered question submitted with a formerly incompatible missing context will still follow its historical route by default. If product requirements demand reference-free handling for those exact strings too, use an explicitly approved versioned request/runtime namespace owned by the backend, with unchanged legacy defaults; do not silently override an exact route. The unseen `What is 4 + 4?` use case can use the new opt-in scope without that override.
