# Restart and Recovery Evidence Matrix

## Scope

This matrix maps the repository's journal implementation, synthetic/fault-injection tests, and recorded filesystem test profile to the restart and recovery scenarios they support. It documents engineering evidence only. **Synthetic crash/recovery testing is not equivalent to a real authorized research collection being interrupted and resumed. No real controlled research-runtime restart/recovery evidence currently exists.** Protected data or Final Test labels and answers are not needed for this evidence summary.

## Platform and durability boundaries

The implementation requires a local POSIX filesystem supporting file and directory synchronization, same-directory atomic replacement, and hard-link create-if-absent. macOS file acknowledgement additionally uses `F_FULLFSYNC`; unsupported synchronization fails closed.

- Windows/Python 3.10 is identified as the authentic calibration host, but is **not supported or certified** for this implementation's POSIX directory-sync durability contract. That history is not platform certification.
- Linux/deployment storage, network filesystems, and special container mounts have not been validated for this contract.
- Physical power-loss behavior and storage-controller/cache guarantees are not certified.
- Network/shared/concurrent-writer scenarios are not certified; the implementation documents a sequential exclusive writer, not shared-writer coordination.
- No exactly-once guarantee for external verifier side effects is established. A durable start/terminal journal can prevent automatic retry of ambiguous work, but cannot prove whether an external side effect occurred.
- `LazyVerifierPool.get()` may construct a verifier before the collector's `on_start` callback. The durable start intent therefore precedes verifier dispatch, but not constructor side effects.

## What remains unproven

The evidence above does not show a real controlled research-runtime collection being interrupted and resumed. It does not establish current runtime/resource compatibility, live service readiness, a supported deployment platform, physical power-loss durability, or exactly-once external execution. A real controlled restart/recovery validation requires an approved runtime configuration, validated resources and platform, and explicit collection authorization. This document makes none of those decisions or authorizations.
